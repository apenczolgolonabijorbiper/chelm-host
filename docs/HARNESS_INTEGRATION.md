# Harness Integration

Chelm-host 0.2.0 implements contract version 1. The following requirements are
from design draft 0.2. See [implementation and verification status](ACCEPTANCE.md)
for measured checks, platform checks awaiting CI, and deviations.

## 8. Harness integration

Chelm-host calls the harness exactly as the reference consumer does today. It also takes over the layout, capability and policy checks that the consumer does not do.

- `HAR-1` Validation, indexing, retrieval and statistics MUST be the harness CLI: `node <harness>/processor/memory-tool.mjs validate --root <dir> [--previous <graph>]`, `... stats --root <dir>`, `... context --root <dir> [options of APP-33]`, and `<python> <harness>/processor/process.py --root <instance>`. Chelm-host MUST NOT re-implement them or import harness modules in-process, except for the public cognitive core/session validators and reference adapter
  openCognition/publishLearning methods described below, to read the harness version and release hashes, and to call `requireCapabilities` from `server/core-policies.mjs` if the backend is built on the harness adapter template (`docs/APPLICATION_PROFILES.md`).
- `HAR-2` Initialization MUST use `<python> <harness>/processor/init-instance.py --root <instance> [--profile]`, never a copy of its templates. (0.10.0 has no `--legacy-layout`.)
- `HAR-3` Layout: Chelm-host MUST take the purpose and hypotheses paths from the `layout` object reported by `memory-tool validate` (`purpose_path`, `hypotheses_path`; in 0.10.0 always `instance/purpose.md` and `memory/hypotheses.json`) and use them everywhere: read model, storage backend protocol files, merge. It MUST NOT keep a fallback to the historical `persona/` paths. An instance that fails layout resolution or uses graph schema 1 is refused with `instance_incompatible` (see `RT-11`). Note for the vendor: `docs/PROCESSING.md` and `docs/ADAPTERS.md` of 0.10.0 still mention historical layouts. `docs/INSTANCE_LAYOUT.md` and `server/instance-layout.mjs` are authoritative.
- `HAR-4` Storage backend: Chelm-host MUST ship a Git backend that satisfies adapter contract v1 (`status`, `claim`, `renew`, `validate`, `commit`, `release-error`) with the semantics in `docs/ADAPTERS.md`, and passes the harness conformance suite (`adapters/conformance/adapter.test.mjs` with `GOLEM_ADAPTER` as a JSON command array) with every applicable test passing.
  - It MUST implement and advertise `candidate-validation-v1`, `purpose-guidance-v2` and `profile-install-v1` and `core-policies-v2`. The last two include immutable claim guidance (`memory/runs/<run>.guidance.json` committed with the claim, `guidance_identity` returned and enforced in the journal at commit), strict hypotheses and dependency validation in the candidate, and refusal of completion when profile, configuration or vocabulary changed in a commit during the lease. `docs/ANALYSIS_WORKFLOW.md` forbids silently using a backend without them when policies are selected. If a capability is missing (for example an older backend), `next` refuses with `capability_missing` when the instance selects a profile or vocabulary.
  - Candidate capture MUST read raw blobs in batches (one `ls-tree` and one `cat-file --batch` per immutable tree, as in 0.10.0), not one Git process per file. It MUST stay within the 64 MiB output budget per child, and refuse clearly when the committed tree exceeds it.
  - It MUST additionally support `claim --ids <list>` and `claim --exclude <list>`. Reservations and integration runs need them; this is an additive extension.
  - The backend's commit set is: HEAD, plus the graph, `memory/index.md`, both question queue files, `memory/hypotheses.json`, the run journal (and its guidance snapshot), the claimed inbox notes and their evidence files, the declared outputs, the new ledger rows and the released lease. The exact tree validated is the tree committed (the consumer's current rule).
  - `validate` and `commit` return the harness warnings with `warning_summary` unchanged. Chelm-host MAY append its own advisory warnings with a `chelm.` code prefix. It never turns a harness error into a warning.
- `HAR-5` Chelm-host MAY use the harness reference adapter unchanged instead of its own backend when delegation is disabled. In 0.10.0 the reference advertises all three capabilities; it lacks only the `--ids` and `--exclude` extension. The choice is recorded in `status.backend`.
- `HAR-6` Profiles: Chelm-host passes the instance's `golem.config.json` profile selection through unchanged. It never writes profile, vocabulary, purpose or configuration files during processing. `chelm profile set --input -` (input `{purpose?, profile?: {core, sections?: [{id, kinds, text}], vocabulary?}}`) writes and commits them as a separate, explicit operation following `docs/APPLICATION_PROFILES.md`. It validates the result with `memory-tool validate` before the commit. It refuses with `busy` while a lease is held, because a committed policy change during a lease makes that run's completion fail (`HAR-10`). The vocabulary is version 2: `kinds`, `predicates`, `single_valued`, `external_id_schemes`.
- `HAR-7` Child processes: arguments are passed as arrays (no shell), stdin closed when unused, Git terminal and credential prompts disabled (`GIT_TERMINAL_PROMPT=0`), `core.autocrlf=false` wherever source bytes are materialized. Timeouts: 60 seconds per Git or validator child, 180 seconds for one backend command (which can run many Git children; the harness's own limit), and 300 seconds for the indexer. Errors name the command.
- `HAR-8` Capacity and bounds MUST come from the harness, not from constants in Chelm-host. `read summary` reports `stats.capacity` (`{sources, entities, claims}` each `{used, limit}`; 0.10.0 limits 10,000, 5,000 and 20,000) and `near_limit` per collection at `ceil(0.8 * limit)`, the harness warning threshold. Submissions MAY be refused early with `capacity_exceeded` when the pending plus processed sources would exceed the source limit; the harness refuses at publication in any case. Retrieval bounds (100 claims, 100 entities, 100 sources, 4,000 characters per source excerpt and 64,000 in total) and the 1,000-warning bound are passed through as the harness reports them.
- `HAR-9` Moving observations between instances follows `docs/PROCESSING.md`, "Moving observations to another instance": inbox and evidence only, pending on the destination, question links resolved before processing (`APP-41`). Selective transfer of processed memory is out of scope until the harness provides it.
- `HAR-10` Policy changes and leases: when `commit` fails because the selected policy changed during the lease, Chelm-host returns `policy_changed` and releases the lease with a fixed safe reason. Unlike other validation failures, the draft outputs are not restored. The result offers a re-claim of the same sources (`claim --ids`, when they are still ready) with a new run ID and the new guidance. The executor must re-check its drafts against the new guidance, write the journal for the new run (with the new `guidance_version` line), and submit again (`WRK-4`).
